# Спецификации прецедентов

Проект: **АИС «Агентство по трудоустройству»**

Практическая работа № 1.2. Проектирование Use-Case диаграммы. Создание спецификаций к прецедентам.

## UC-01. Подать заявку на вакансию

| Параметр | Содержание |
|---|---|
| **Идентификатор** | UC-01 |
| **Название** | Подать заявку на вакансию |
| **Акторы** | Соискатель |
| **Цель** | Оформить отклик на выбранную вакансию и передать заявку агенту по трудоустройству для дальнейшей работы. |
| **Предусловия** | • пользователь авторизован в системе с ролью «Соискатель»;<br>• в системе имеется хотя бы одна опубликованная вакансия;<br>• у соискателя заполнено резюме, которое можно приложить к заявке. |
| **Постусловия** | • в базе данных создана заявка со статусом «Новая»;<br>• заявка связана с выбранными резюме и вакансией;<br>• агент по трудоустройству видит новую заявку в реестре заявок;<br>• соискателю отображается подтверждение и текущий статус заявки. |
| **Основной сценарий** | 1. Соискатель открывает раздел «Поиск вакансий».<br>2. Система выводит список опубликованных вакансий с фильтрами по должности, заработной плате, типу занятости и работодателю.<br>3. Соискатель задаёт критерии поиска и выбирает подходящую вакансию.<br>4. Система открывает карточку вакансии с обязанностями, требованиями и сведениями о работодателе.<br>5. Соискатель нажимает кнопку «Подать заявку».<br>6. Система проверяет наличие заполненного резюме и отсутствие ранее поданной заявки на эту вакансию.<br>7. Соискатель выбирает резюме из списка и подтверждает отправку заявки.<br>8. Система создаёт заявку со статусом «Новая», фиксирует дату и время и уведомляет агента по трудоустройству.<br>9. Система выводит сообщение об успешной подаче заявки и её номер. |
| **Альтернативные сценарии** | A1. На шаге 6 резюме отсутствует или не заполнено. Система предлагает перейти к форме резюме; после сохранения резюме соискатель возвращается к вакансии и повторяет подачу заявки.<br>A2. На шаге 6 заявка на данную вакансию уже существует. Система предупреждает соискателя и предлагает открыть существующую заявку либо отменить действие.<br>A3. На шаге 7 соискатель отменяет подтверждение. Заявка не создаётся, система возвращает пользователя в карточку вакансии. |
| **Исключения** | • вакансия снята с публикации или переведена в статус «Закрыта» — система сообщает об этом и предлагает выбрать другую вакансию;<br>• отсутствует соединение с сервером или произошла ошибка сохранения — система выводит сообщение об ошибке и не создаёт частичную запись;<br>• учётная запись соискателя заблокирована — система отказывает в подаче заявки и предлагает обратиться к администратору. |
| **Связанные прецеденты** | Связан с прецедентами «Авторизоваться» (include), «Найти вакансию», «Просмотреть статус заявки». |

## UC-02. Оформить трудовой договор

| Параметр | Содержание |
|---|---|
| **Идентификатор** | UC-02 |
| **Название** | Оформить трудовой договор |
| **Акторы** | Агент по трудоустройству; второстепенные — соискатель, работодатель |
| **Цель** | Оформить трудовой договор по подтверждённой сделке и перевести трудоустройство в завершённое состояние. |
| **Предусловия** | • агент по трудоустройству авторизован в системе;<br>• существует сделка в статусе «Подтверждена»;<br>• в сделке указаны соискатель, работодатель, вакансия и согласованные условия;<br>• заполнены обязательные реквизиты договора: номер, дата, срок, должность, оплата труда. |
| **Постусловия** | • создан трудовой договор с уникальным номером, привязанный к сделке;<br>• сделка переведена в статус «Трудоустроен»;<br>• договор доступен для просмотра и печати;<br>• соискатель и работодатель уведомлены о заключении договора. |
| **Основной сценарий** | 1. Агент открывает раздел «Сделки».<br>2. Система отображает реестр сделок с фильтрами по статусу, дате, соискателю и работодателю.<br>3. Агент выбирает сделку со статусом «Подтверждена».<br>4. Система открывает карточку сделки с данными сторон, вакансии и условиями трудоустройства.<br>5. Агент нажимает кнопку «Оформить трудовой договор».<br>6. Система формирует проект договора: номер, дату, сведения о соискателе и работодателе, должность, срок и условия оплаты.<br>7. Агент проверяет проект и при необходимости корректирует данные.<br>8. Агент подтверждает создание договора.<br>9. Система сохраняет договор, присваивает статус «Действует» и переводит сделку в статус «Трудоустроен».<br>10. Система формирует печатную форму договора и уведомляет соискателя и работодателя. |
| **Альтернативные сценарии** | A1. На шаге 3 сделка не находится в статусе «Подтверждена». Система блокирует оформление договора и предлагает сначала завершить сделку.<br>A2. На шаге 7 не заполнены обязательные реквизиты. Система подсвечивает поля, выводит перечень ошибок и не позволяет сохранить договор до их устранения.<br>A3. На шаге 8 агент отменяет создание. Договор не создаётся, сделка остаётся в прежнем статусе. |
| **Исключения** | • договор с указанным номером уже существует — система предлагает изменить номер или открыть существующий договор;<br>• ошибка формирования печатной формы — договор сохраняется, но система выводит сообщение и предлагает повторить формирование документа;<br>• у агента отсутствуют права на оформление договора — операция блокируется, выводится сообщение о недостаточных правах. |
| **Связанные прецеденты** | Связан с прецедентами «Оформить сделку» (include), «Подобрать кандидатов», «Сформировать отчёты». |

## UC-03. Управлять учётными записями пользователей

| Параметр | Содержание |
|---|---|
| **Идентификатор** | UC-03 |
| **Название** | Управлять учётными записями пользователей |
| **Акторы** | Администратор |
| **Цель** | Создавать, изменять и блокировать учётные записи пользователей, обеспечивая актуальность прав доступа. |
| **Предусловия** | • администратор авторизован в системе;<br>• открыт раздел администрирования;<br>• администратор обладает правом управления учётными записями. |
| **Постусловия** | • учётная запись создана, изменена или заблокирована;<br>• изменения сохранены в базе данных и зафиксированы в журнале действий;<br>• пользователь уведомлён об изменении статуса или данных учётной записи. |
| **Основной сценарий** | 1. Администратор открывает раздел «Пользователи».<br>2. Система выводит список пользователей с поиском и фильтрами по роли и статусу.<br>3. Администратор выбирает пользователя или нажимает кнопку «Добавить».<br>4. Система открывает форму учётной записи.<br>5. Администратор заполняет или изменяет фамилию, имя, отчество, логин, email, роль и статус учётной записи.<br>6. Система проверяет уникальность логина и email, корректность адреса электронной почты и обязательность полей.<br>7. Администратор сохраняет изменения.<br>8. Система сохраняет учётную запись и записывает действие в журнал администрирования.<br>9. Система уведомляет пользователя об изменениях. |
| **Альтернативные сценарии** | A1. На шаге 3 администратор выбирает блокировку пользователя. Система запрашивает подтверждение и после подтверждения устанавливает статус «Заблокирован». Данный сценарий детализируется прецедентом «Заблокировать пользователя», который расширяет базовый прецедент.<br>A2. На шаге 6 логин или email уже заняты другим пользователем. Система сообщает об ошибке и предлагает изменить значения.<br>A3. На шаге 7 администратор отменяет изменения. Данные не сохраняются, форма закрывается. |
| **Исключения** | • у администратора недостаточно прав — операция блокируется;<br>• попытка заблокировать или удалить собственную учётную запись — система запрещает действие;<br>• ошибка записи в базу данных — изменения отменяются, выводится сообщение об ошибке. |
| **Связанные прецеденты** | Связан с прецедентами «Авторизоваться», «Заблокировать пользователя» (extend), «Вести справочники». |
